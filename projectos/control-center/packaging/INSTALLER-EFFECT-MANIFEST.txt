INSTALL LOCATION - FIXED, NOT CHOSEN

  ProjectOS refuses to run an installation whose recorded install root does not match
  the directory the executable actually runs from. An installer that let a user pick a
  different directory would therefore offer a choice that produces an installation
  ProjectOS will not launch. The choice is removed rather than the check weakened.

  Evidence, read from this MSI:

  1. the directory dialog does not exist in this installer:
       ABSENT. InstallDirDlg is not in the Dialog table - not merely skipped.

  2. no control of any kind can browse or type a directory:
       NONE. No PathEdit, DirectoryCombo or DirectoryList control exists.

  3. no feature may be redirected (ConfigurableDirectory must be empty for all):
       ShortcutsFeature | 
       MainProgram | 
       Environment | 
       External | 

  4. nothing searches for a previous install directory. AppSearch sets only:
       INSTALLED_WEBVIEW2_VERSION | Webview2VersionSystemx64
       INSTALLED_WEBVIEW2_VERSION | Webview2VersionSystemx86
       INSTALLED_WEBVIEW2_VERSION | Webview2VersionUser
       INSTALLDIR is absent from that list, so no stale registry value from an earlier
       install can silently relocate this one.

  SCOPE OF THIS CLAIM. This concerns the NORMAL INSTALLER USER FLOW: what a person
  running the MSI can choose. It is NOT a claim that the install root cannot be
  overridden at all. An administrator can still pass INSTALLDIR=... on an msiexec
  command line, and Windows Installer will honour it. That is not defended against
  here, and it is not silent: such an installation records one root, installs to
  another, and ProjectOS REFUSES to launch it. The failure is loud and fails closed.

  KNOWN LIMITATION - THE SYSTEM DRIVE IS ASSUMED TO BE C:. INSTALLDIR resolves from
  ProgramFiles64Folder, which follows the drive Windows is installed on, but the
  installed-application record is composed once at BUILD time and hardcodes C:. On a
  machine where Windows is not on C:, a LEGITIMATE untampered install would be
  refused at launch. That fails closed, not open - a reliability defect, not a
  security one - but it is a real installation path this MSI permits and ProjectOS
  would refuse. Closing it requires composing the record at INSTALL time via a custom
  action, which is an OWNER DECISION and is deliberately not taken here.

  The installer AUTHORS the canonical installed-application record at
  <ProgramData>\ProjectOS\host\installation\application.v1.json.

  That record is what gives an installation its corroborating per-machine evidence
  and names the governed ProjectOS SYSTEM root. It carries no secret, no key
  material and no trust anchor: it states installation facts, and the governed root
  it names is only ever consumed through the sealed boundary that demands a verified
  packaged identity. A record without a verified application is worth nothing.

UNINSTALL / ROLLBACK
  Standard Windows Installer semantics. Every file above belongs to a component keyed
  to this ProductCode, so uninstall removes exactly those files and the shortcuts, and
  a failed install rolls back through the installer transaction. An Uninstall shortcut
  invoking msiexec is installed alongside the application. ProgramData IS touched: the
  installed-application record is written there, and the RemoveFile entries above take
  it and its directories away again on uninstall.
